## 1. 项目要做什么

基于 [foliate-js](https://github.com/johnfactotum/foliate-js) 改造一个 AI 漫画小说阅读器：

1. 导入纯文本书籍，流畅阅读，界面简洁，响应式适配桌面与移动端。
2. 接入**可配置**的文本大模型 API，把书籍内容按**可配置**的分段策略切分，自动挑选适合绘图的片段。
3. 通过**可配置**的 API 或本地画图模型，把片段生成漫画分镜。
4. 依据小说设定**自动提取并固定人物外貌特征**（发型、服饰、体型、年龄等），保证各分镜人物一致且符合原文。
5. 分段策略、提示词模板、风格参数、模型接口全部可配置，最终输出**连续的漫画页面**。
6. 支持**参考图注入**模式：预绘人物形象图 → 作为参考图 + 人物身份说明一起传给画图模型。

追加需求：

7. **变身类设定**：变身前后数据与状态如何衔接、编辑节点如何适配切换、边界与冲突、推荐方案与备选。
8. **AI 辅助阅读**：文本模型读正文与漫画内容、概括大意、支持对话交互。

测试书籍：`book/` 目录（1 个 TXT + 1 个 EPUB，同一本书）。

## 4. 不要重新踩的坑（全部【实测】，除非注明）

### 4.1 MOSS 编辑链路

| 现象 | 原因 | 正确做法 |
| --- | --- | --- |
| `required_input_missing: image_0` | Autogrow 输入用嵌套字典序列化 | 必须用点号扁平键 `"images.image_0": ["6",0]` |
| `mat1 and mat2 shapes cannot be multiplied (43x2048 and 4096x3072)` | 2b 编码器（3072 维）配 MOSS（4096 维） | 用 9B 编码器，或 `MossCLIPLoader` + adapter（0.8b/2b/4b 的 adapter 已有） |
| `image_strength` 调了没反应 | `Moss-Image-Edit` 格式下 vision 通道关闭，该参数不参与计算 | 该格式下不要暴露此参数 |
| 参考图接上就构图错位 / 显存暴涨 | 参考图按原尺寸进 latent | 先 `ImageScale` 到目标画幅再喂 |
| 多张参考图顺序混乱 | 节点内部 `sorted(images)` 字符串排序，`image_10` 排在 `image_2` 前 | 单请求 ≤3 张，命名 `image_0..` |

`edit_format` 三种的真实差异（源码 `comfy_extras/nodes_moss_image.py`）：

| 选项 | reference method | 视觉通道 | 行为 |
| --- | --- | --- | --- |
| `ai-toolkit` | `index_timestep_zero_isolated` | 开 | 文本能用 Picture N 指代图 |
| `ai-toolkit (kv_cache off)` | `index_timestep_zero` | 开 | 参考图每步重算，更贴图更慢 |
| `Moss-Image-Edit` | `index_timestep_zero_text_start` | **关** | 只有 latent 约束，最稳最不串 |

### 4.2 多参考图不能表达"变身"（三次对照实验）

| format | 意图 | 结果 |
| --- | --- | --- |
| `Moss-Image-Edit` | 只描述形态 A | 输出≈A，第二张图完全无痕 |
| `ai-toolkit` | 换成 B 的发色服装 | 指令生效，但整体形象变成 B |
| `ai-toolkit` | 只把 A 的头发改蓝 | **属性混叠**：蓝短发+橙长发并存、书+鲸鱼同抱、白裙配深蓝袖 |

结论：模型把多图当作"同一个体的多视角"，不是两个不同个体。**多图注入不能做特征路由**。

### 4.3 分段打分

- 用 sigmoid 归一化会导致 p50=0.97 全部顶到 1，排序失效。**必须用语料内百分位**（`bisect`）。
- 特征计数要 `tanh` 压缩，否则长片段天然计数偏高。

### 4.4 其他

- 本书编码是 `utf-8-sig`（不是 utf-8），开头有 11 行书籍元信息 + `【简介】` + 章首标签行 `【类型标签】`，不清理会污染第一个片段。
- 章节正则 `^第N章` 命中 234 次，与实际一致；但需要"前 3 章内命中 ≥2 次"才认定为章节体，否则退化为定长切章。

## 5. 项目可能存在的问题

### P0 — 阻断级 / 决定项目可行性

1. **一致性从未实测**。只验证了"单格 20 秒能出图"，没做过"同一角色 10 格的人脸相似度横评"。整个一致性方案（冻结身份卡、种子族、参考图注入、阈值 0.55）都建立在未验证的假设上。
2. **双形态同框必然混叠**（已实测）。只能拆格或分层合成，分层合成（RMBG 抠图拼接）也未验证。
3. **12GB 显存锁死单并发**。9B 编码器 9.75GB + int8 底模 5.4GB 超显存，靠 offload 硬撑。全书约 900 格，估计精修 14h / 草稿 3.5h（【推断】，基于 20s/格实测外推）。
4. **没有任何应用代码**。所有结论都是设计推演 + 节点实测，工程风险未暴露。

### P1 — 中等，会影响质量或工期

5. **人脸校验阈值未校准**。0.55 是 ArcFace 真人经验值，插画人脸分布不同，直接套会误杀；建议 0.45 起步用实测定标。
6. **分段 LLM 层未验证**。JSON 合规率、角色识别正确率、`drawable` 打分与人工判断的一致性，全部没有数据。而这层决定"谁在场、什么动作"——画错人的根源在这。
7. **人物卡抽取从未在真实文本上跑过**。尤其是"变身前后"字段能否稳定抽出、LLM 会不会把代词（他/她）当性别依据，未知。
8. **本地模型缺位**：`models/LLM` 空 → 外部漫画 caption、本地摘要生成都做不了，只能挂远程 API。
9. **foliate-js 自述"不稳定，API 可能变"**。需锁 submodule commit，适配层只依赖 `open` / `relocate` / `sections` 三个契约。
10. **TXT 清洗只验证了这一本书**。GBK 编码、无章节标记、超长单章、含插图标记的 txt 都没测过。

### P2 — 设计待定 / 需要人决策

11. **形态切分点未确认**：形态转折章是否已确认？后面有没有二次变身？这决定形态表怎么建。
12. **漫画文字方案未验证**：设计上定的是"图不带字，排版层后置绘制"，但中文气泡的字体、换行、字号自适应没做过。
13. **成本估算只算了时间**，没算 API 费用差异（本地 vs 远程差一两个数量级）。
14. **版权与内容安全**：仅承诺处理用户本地文件，但导出 CBZ / 分享链接的合规边界没定。
